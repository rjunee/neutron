# IMPLEMENTATION_PLAN — Work Board card removal: agent-exposed, run-cancelling, reason-carrying, doc-disposing (+ a shelved lane)

Governing spec: this Plan card (agent remove through the UI's own path; archived ≠ done; removal takes a reason and the plan doc's disposition follows it; removed = really gone). Verified against main 2026-08-14:

- MEASURED: the capability exists UI-side only. `gateway/http/work-board-surface.ts` `handleDelete` (496–565) cancels a live trident run via the §F6a `terminate()` chokepoint (claiming `cancelled_run` only when the atomic transition is `won`) and a research run via `cancel_dispatch` (DispatchService.stop), then `store.delete`s the row. `work-board/store.ts.delete()` is a real `DELETE FROM` — acceptance (d) already holds at the store layer.
- MEASURED gaps: `work-board/agent-tool.ts` registers `list/add/update/complete/reorder` only — no remove tool, so the agent's only removal lever is `complete` (the misreport). No `archived` status anywhere (0097 CHECK is `upcoming/in_progress/done/failed`; `failed` is run-driven, not a shelf). Removal takes no reason; no code path ever moves or names a card's `plans/<slug>.md` doc on removal (`docs/plans/cancelled/` exists only as a hand pattern in the vault). `DocStore.moveDoc` exists and is unused by the board.
- Layering constraint: `work-board/package.json` has NO trident dep — the shared removal chokepoint must take structural deps (run access + `is_terminal_phase` fn + doc mover), exactly the shape `open/composer.ts`'s `boardRunAccess` facade (~3630) and the surface's `TridentRunAccess` already have.

- [x] **T0 — (already built) UI X cancels an in-flight run before deleting the row, atomically-claimed, observer-chain included** (§F6a terminate chokepoint + dispatch stop; `store.delete` is a hard row delete). This is the path the new chokepoint must extract and preserve byte-for-byte in behaviour, not reimplement.
- [x] **T1 — the removal CHOKEPOINT: `work-board/removal.ts` — reason-taking, run-cancelling-first, doc-disposing remove; rewire the HTTP DELETE through it; pin the live-run-cancellation ORDER with a mutant-red test.** New `WorkBoardRemovalService.remove(scope, docs_project_id, item_id, { reason: 'shipped'|'cancelled'|'moved', plan_doc?: 'delete' })`: (1) cancel a live bound run FIRST (build → terminate/update fallback, research → dispatch stop — the existing handleDelete logic moved verbatim, best-effort), (2) dispose the plan doc — an in-app `plans/…` ref MOVES to `plans/<reason>/<basename>` via `DocStore.moveDoc`; a move failure leaves it in place and logs; ONLY an explicit `plan_doc:'delete'` may delete; (3) hard-delete the row. HTTP `DELETE …/work-board/<id>` gains `?reason=` (default `cancelled` — the X's semantics today) + `?plan_doc=delete`; response keeps `deleted`/`cancelled_run` and adds the doc disposition. Composer builds ONE service and hands it to the surface. Tests: cancellation ordering asserted as an event sequence so the skip-cancellation mutant AND the delete-first mutant both go RED; no implicit path ever calls deleteDoc; removed card is gone from `list()`/`get()` against a real store.

GENERAL_WORK_BOARD_PROJECT_ID`, mirroring add — the scope/docs-id conflation hazard is documented in `spec-doc-service.ts`).
