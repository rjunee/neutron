# IMPLEMENTATION_PLAN — Host-deploy approval must be usable where it lands (Plan card 2026-08-15)

Governing spec: this Plan card. Verified against main `d8324cc` 2026-08-15:

- ROOT CAUSE CONFIRMED IN CODE: `open/composer.ts:2605` (`approval_topic_id: resolveAppWsReminderTopic(null)`) and `:2607` (`deliver(resolveAppWsReminderTopic(null), …)`) hard-code the owner topic for every host-deploy approval; `resolveAppWsReminderTopic` (`composer.ts:2510-2511`) ignores its argument and always returns `appWsTopicId(OWNER_USER_ID)`.
- THE THREAD ALREADY EXISTS: `ToolCallContext.topic_id` (`tools/registry.ts:86-87`) carries the calling chat topic into every tool handler (`mcp/server.ts:154,274`); the `host_deploy_request` handler (`gateway/wiring/host-deploy-tool.ts:148`) simply never reads `ctx`. The owner-tap capture (`gateway/wiring/build-live-agent-turn.ts:1150-1179`) windows prompts on `turn.topic_id`, so a prompt raised on the requesting topic resolves there with NO capture change — no second mechanism.
- `HOST_DEPLOY_APPROVAL_TTL_MS = 5 * 60_000` (`open/host-deploy.ts:143`) is enforced on the ANSWER only (`:740-748`); `button_prompts.expires_at` is effectively never, so a dead grant leaves a live-looking button.
- The body's last line (`host-deploy.ts:441`) says typing won't work; the `hdp:` token appears only in `button_prompts.options_json` — no surface renders it (T3, measured).
- The four-prompt eviction seam is self-documented at `host-deploy.ts:684-690` — an evicted token returns null and falls through to the LLM (T4).
- `ApprovalManager.expireStale()` (`tools/approval.ts:187`) has no production caller; `open/wiring/approval-notifier.ts:69-83` pushes ONE `agent_message` frame to `registry.topics()` with no retraction; `landing/chat-react/controller.ts:1436,1441` appends `this.notices` after the durable transcript unconditionally with no dismissal path (T5/T6, measured).

- [x] **T1 — raise the Approve/Deny prompt on the topic that requested the deploy; the tool result names the destination.** Thread `ctx.topic_id` from the `host_deploy_request` handler into `HostDeployService.request({ ref, topic_id })`; the service resolves `approval_topic = topic_id ?? fallback` (fallback = the owner General topic, unchanged for system/cron callers), passes it to `approvals.requestApproval({ topic_id })` AND to a topic-carrying `emit` (`HostDeployEmit` gains `topic_id`; composer's emit delivers to `p.topic_id` instead of `resolveAppWsReminderTopic(null)`). `pending_approval` result gains `approval_topic_id`, plus a `note` naming the destination whenever it differs from the requesting topic, and the tool description tells the agent to always say WHERE the button is. Acceptance (card, verbatim): a request raised from `app:owner:<project>` puts its prompt on `app:owner:<project>` — assert `button_prompts`/emit topic equals the requesting topic, not the owner topic.
- [ ] **T2 — a dead grant must not leave a live-looking button, and a stale tap must re-raise instead of dead-ending.** On the TTL-expired answer path (`host-deploy.ts:741-748`), and on the stale-sha refusal, automatically re-run the request pipeline pinned to a fresh resolve of the same ref and say so in one sentence ("that one expired — here is a fresh commit list") — still a real owner decision, never an auto-approve. Expire/disable the ButtonStore prompt row alongside the grant (the prompt currently outlives it by a decade: `button_prompts.expires_at` ≈ 2036).
- [ ] **T3 — print the typed fallback IN the approval body.** Replace the "Typing anything else will NOT approve this deploy" dead-end with the two exact strings that DO work (`hdp:<token>:a` / `hdp:<token>:d`), rendered in the body `renderHostDeployApprovalBody` builds, so the one string that works when buttons are unreachable is visible to a human, not only to the database.
- [ ] **T4 — an evicted prompt's tap must say so.** In `handleOwnerButtonAnswer`, when `HOST_DEPLOY_VALUE_RE` matches but the value is NOT in `prior_option_values`, return a sentence explaining the prompt aged out of the answer window and (per T2) re-raise — never return null and let a raw `hdp:` token fall through to the LLM as unexplained text. Closes the seam the code itself documents at `host-deploy.ts:684-690`.
- [ ] **T5 — `expireStale()` gets a real production caller, and expiry is visible.** Wire a periodic sweep (loop-registry registered, e.g. alongside the approval module init in `gateway/composition/build-core-modules.ts:294-306` or the reminders tick) so a pending `tool_approvals` row past TTL transitions to `expired` without waiting for a tap; the notifier must not announce a grant already past its TTL; an expired grant is distinguishable from an unanswered one in what the owner is told.
- [ ] **T6 — the approval banner must be dismissible and must not outlive its grant.** `open/wiring/approval-notifier.ts` sends a retraction frame (or the banner derives from the row) when a grant is decided/expired; `landing/chat-react/controller.ts` gives ephemeral notices a dismissal path and stops pinning them below messages that arrived after them (`:1436,1441` — arrival-order sort, no unconditional tail). Assert: send a notice, then a user message, and the notice does NOT render last; a decided/expired grant's banner disappears without a page reload.
