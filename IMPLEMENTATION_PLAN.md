# IMPLEMENTATION_PLAN — Credentials orphaned by a changed owner handle: migrate at boot, and stop calling it "not connected" (card 2026-08-14)

Governing spec: this Plan card (owner-approved design 2026-08-14 — unambiguous ⇒ auto-migrate + audit; ambiguous ⇒ touch nothing, surface `orphaned` + a migrate action; NEVER refuse boot). Verified against main 2026-08-14:

- The #451 rename reconciler (`migrations/scope-rekey.ts`, wired at `gateway/index.ts:283-342`) already sweeps `secrets.project_slug` and `project_credentials.owner_slug` — but ONLY when the `instance_scope_ledger` disagrees with the boot slug. On this box the ledger was seeded as the boot slug at first boot, so rows written pre-provisioning under `dev` are invisible to it forever: the every-boot path is a single SELECT noop. Nothing in the tree detects credential rows scoped to a non-boot handle when the ledger agrees. This is the gap the card names.
- `SHARED_KEY_ENCRYPTED_TABLES` (`auth/secrets-store.ts:79`) = `['secrets', 'project_credentials']`; scope columns are `secrets.project_slug` and `project_credentials.owner_slug` (per `migrations/scope-rekey.ts:153,162`). `api_keys.project_slug` is the metadata twin the BYO-key read path keys off (`gateway/cores/integrations.ts:120-133`) — moving `secrets` without it leaves BYO keys half-orphaned.
- `buildIntegrationsStatus` (`gateway/cores/integrations.ts:262`) and `integrations_list` (`gateway/cores/integrations-tools.ts:79`) report presence-only (`connected: false`) — a wrong-scope miss and "never connected" are the same sentence. No orphan concept exists anywhere in `gateway/cores/`.
- Audit precedent: boot journals `instance_scope_rekeyed` through `SystemEventsStore` (`persistence/system-events.ts:85`, `gateway/index.ts:312-342`); the sink is registered BEFORE the reconcile band, so a new boot step there is journalable.

Module header records the reminders decision (out of scope: `reminders.project_slug` is the renameable boot-slug axis, not a shared-key credential table — whether that scope key belongs there at all is undecided; no rows moved here). Tests pin acceptance (a), (a2 rotation hazard — assert the DECRYPTED fresh value survives), (a3 never-refuse via a real `boot()`), (c both tables + api_keys), (d no secret material in result/log/audit), and the delete-the-migration-turns-red mutation guard.
- [ ] **T2 — a miss is DISTINGUISHABLE (acceptance b).** Extend `buildIntegrationsStatus` (`gateway/cores/integrations.ts`) with an `orphaned_credentials` summary — per-table, per-handle row counts of credential rows scoped to a non-boot handle (one cheap GROUP BY per swept table, reusing T1's sweep map; no decrypt, no secret material) — and per-slot annotation: an `oauth`/`api_key` slot that reads disconnected but has an orphaned row for the same service/label reports `orphaned: true` ("scoped to a previous handle"), never bare `connected: false`. `integrations_list` (`gateway/cores/integrations-tools.ts`) surfaces the summary and names the migrate action. Tests: seeded orphan rows ⇒ status says orphaned/needs-migration; positive control — the same lookup under the correct handle reports connected; a genuinely-unconnected slot still reads plain `connected: false`.

Expose as agent tool `integrations_migrate_orphaned` (`approval_policy: 'prompt-user'`) in `integrations-tools.ts` + a POST on the integrations HTTP surface (`gateway/http/cores-oauth-surface.ts` band), both through the one brain. Journal `credential_scope_migrated` with moved/skipped counts. Tests: colliding row skipped AND the fresh decrypted value survives (assert the value, not the row count); non-colliding rows move and read back; response carries no secret material.
