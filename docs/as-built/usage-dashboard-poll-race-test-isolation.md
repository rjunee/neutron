## 2026-09-25 — Isolate the usage poll race test's fetch gates

Refs #1301. The shared-host device lane failed one of 411 tests: the slow-poll case expected two held fetches and saw three. The candidate change under test touched only the REPL model-control test and its as-built record; the usage screen and this test were unchanged from the base. The failed run did not record the third request's URL, so its source cannot be attributed retrospectively. The same usage case had previously failed in a co-resident device lane and passed in isolation (see `voice-note-fetch-attempt-isolation.md`).

The race fixture replaced the process-wide `fetch` and treated *every* request as a usage dashboard poll. A controlled unrelated `data:` request during the overlap reproduced the host's exact `expected 2, received 3` gate-count failure with the old interception rule. The fixture now gates only `/api/app/usage/dashboard` and forwards every other URL to the fetch implementation it replaced. Its probe verifies that an unrelated request reaches that prior implementation, returns successfully, and leaves the two dashboard gates unchanged. The prior fetch is restored at the end of the case.

The production sequence guard is unchanged. Removing it under a controlled mutation still made the corrected test fail at its final rendered assertion: expected `75%`, received `25%` after the older response landed last. With the fix restored, the focused case passed, app and root TypeScript checks passed, and the exact 43-file device lane passed 411/411. This establishes that the test still detects the screen rolling backwards while no longer counting an unrelated fetch as a poll; it does not identify the third request in the original host log.
