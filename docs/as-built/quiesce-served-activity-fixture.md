## 2026-10-09 — Quiesce the served activity fixture before DB close

`open/__tests__/activity-inspector-served.test.ts` boots the real Open composer for each served case. Its `withComposition` teardown used to call every registered cleanup without awaiting it and then close SQLite at once, so a composed loop could still be writing when the DB closed. The teardown now awaits the existing production drain, `drainRealmodeCleanups` from `gateway/index.ts`, before `db.close()`. The drain runs callbacks in registration order and continues past a rejection. There is no catch, so a body failure still propagates after cleanup. The body also receives the fixture's `db` and `composition`. Production code and shared test support are unchanged, and all instrumentation lives in this test file.

The file adds four regressions. Two of them hold the real composed `chunked-upload-sweeper` SupervisedLoop tick: one for a body that returns, one for a body that throws. Each test seeds a known expired row that is still `uploading`, checks that `listExpiredUploading` returns it, and drives the captured loop's `runOnce()`. The tick enters a barrier placed in front of the real `SqliteUploadSessionStore.markExpired`. While the tick is held, the teardown is blocked inside the sweeper's quiescing `stop()`. At that point the test asserts that teardown has not settled, the DB has not closed, and the row can still be read as `uploading`. After release it checks the ordered events: `markExpired:entered`, then `sweeper.stop:start`, `markExpired:wrote:true`, `sweeper.stop:end`, `db:closed` and finally `teardown:settled`. It also checks that the loop is inactive, that each of the 20 registered cleanups ran exactly once, that the throwing variant's original error survived, and that the row reads `expired` after the file is reopened. A third regression places a rejecting cleanup before a held cleanup. It verifies the order, that neither is skipped, that the DB stays open while the second is held, exact-once counts, and that no unhandled rejection occurs. The fourth is a control with no registered cleanups, which closes once and leaves the sweeper inactive. Waits are resolved by recorded events and have a labelled 10 s guard deadline. Every test's `finally` releases its barrier and awaits the fixture's disposal.

`bun test open/__tests__/activity-inspector-served.test.ts` gave 12 pass, 0 fail, 94 `expect()` calls. These are the 8 original served cases and the 4 new regressions, and the run was repeated after every mutation was restored. Each mutation was applied on its own to the fixture's `finally`, and the file was restored byte-identical (same SHA-256) afterwards:

- **Drain not awaited** (`void drainRealmodeCleanups(...)`): 9 pass, 3 fail. Both held-tick variants and the rejection case failed the while-held assertion, with `teardownSettledWhileHeld` and `dbClosedWhileHeld` both `true`.
- **DB closed before the drain:** 9 pass, 3 fail. The same three cases failed the while-held assertion on `dbClosedWhileHeld: true`.
- **Drain invoked twice:** 9 pass, 3 fail. The same three cases failed the exact-once assertion: `cleanupRunsPerTeardown` was 2 for every registered cleanup.

The no-cleanup control and the 8 served cases passed under all three mutations.

This record covers only this fixture's teardown ordering. It does not claim that this fixture resolves every source of #1389's historical CI noise. The integration, route-slot and durable-chatlog fixtures are separate work.
