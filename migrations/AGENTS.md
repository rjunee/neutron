# AGENTS.md — migrations

This module owns the SQLite schema migration layer. Raw `*.sql` files named `<NNNN>_<name>.sql` are applied lexicographically (4-digit prefix is a version), forward-only, tracked in the `_migrations` table. **APPLIED-ONCE IS ENFORCED BY THE LEDGER, NOT BY EVERY STATEMENT BEING RE-RUNNABLE** — the runner reconciles by migration NAME (`runner.ts` `classifyMigration`) and writes each body plus its ledger row in ONE transaction, so a migration either lands and is recorded or neither. The files themselves are a mix: 34 of the 123 use bare `ALTER TABLE … ADD COLUMN`, which fails on a second run, and 34 use `CREATE TABLE IF NOT EXISTS` (measured 2026-08-17). So never assume re-running a file is safe — rely on the ledger, and prefer `IF NOT EXISTS` in new files because it makes a hand-recovered instance cheaper to repair. The runner lives in `runner.ts` (~80 LOC, `bun:sqlite`); first migration is `0001_initial_schema.sql`, lifted from Hermes `hermes_state.py:30-110` (sessions + messages + FTS5 + WAL pragma) with Neutron columns added inline (`core_id`, `project_id`, `substrate_instance_id`, `channel_binding_kind`, `channel_binding_address`, `privacy_mode`).

It must NOT include `down` migrations (forward-only is the locked direction per `docs/engineering-plan.md § B.P0` + § E), pull in third-party migration tooling (the runner is small enough to own; cross-validate against `bun-sqlite-migrate` shape but do not depend on it), or ship per-Core data shapes (per-Core tables land in P3 migration files following the same pattern).

Run via `bun run migrations/runner.ts <db-path>` or `bun run migrate <db-path>`. Tested via `bun test migrations/runner.test.ts`.
