# IMPLEMENTATION_PLAN.md — REPL effort pin + resolved-settings echo (twin of #345, Claude side)

Governing doc: the Plan-card spec "The REPL launcher pins the model but never the reasoning effort — and nothing echoes the resolved value". Verified against the code at `runtime/adapters/claude-code/persistent/`: `buildReplArgv` (build-repl-argv.ts) emits `--model` LAST and no effort flag anywhere; `buildSettings` (build-settings.ts) writes a hooks-only settings JSON (no model/effort keys); `spawn.ts` sets no `*EFFORT*`/`*THINK*` env on the child; the registry row (`ReplRegistryRecord`, repl-registry.ts) stores `model` but not effort. The defect is exactly as the spec states, and none of T1–T4 is started.

- [x] Baseline confirmed: the codex twin (#345) is DONE and is the pattern to mirror — `trident/codex-build.sh` pins `model_reasoning_effort=xhigh` behind `${CODEX_BUILD_EFFORT-xhigh}` with a why-comment, and `trident/codex-build.test.ts` ("the reasoning effort is PINNED, and overridable…") goes red if the pin is dropped. The Claude REPL side has no equivalent (verified 2026-08-17; installed `claude` 2.1.198 supports `--effort <level>`, valid set probed live: low, medium, high, xhigh, max — and an UNKNOWN value is a mere warning that silently falls back to the default, the #345 value-not-key trap).
- [x] T1 — Pin reasoning effort explicitly in the REPL launcher: add an `effort` seam to `buildReplArgv` (emitted `--effort <v>` immediately before the model-LAST pin), a `resolveReplEffort()` single-binding resolver (options.effort → NEUTRON_REPL_EFFORT env → DEFAULT_REPL_EFFORT `'high'`; explicit empty string = deliberate unpin), thread it through `spawn.ts` + `PersistentReplSubstrateOptions`, with the why-comment recorded at the default literal and unit tests in `__tests__/build-repl-argv.test.ts` (default emitted, value in the CLI-accepted set, override, empty-string omit, model still last).
- [ ] T2 — Echo the RESOLVED settings at launch: from the SAME `resolveReplEffort` binding that fed argv, (a) stamp `effort` onto the `ReplRegistryRecord` row `spawn.ts` already writes (next to `model` — readable without a database, it is a JSON file), (b) write a per-session launch record `${cfgBase}-launch.json` (0600, in the 0700 cfgDir) carrying resolved model, effort, sessionId, tool surface, settingsPath and spawn time, added to `session.configPaths` for teardown, and (c) print a one-line stderr launch banner `[repl-launch] session=<id8> model=<model> effort=<effort> tools=<n> settings=<path>` the way codex's banner reads back its settings.
- [ ] T3 — Make it answerable from inside: replace the shared `--append-system-prompt-file` pass-through with a per-session generated prompt file (`${cfgBase}-prompt.md` = base-prompt bytes + a "Launch record" stanza stating the resolved model and effort and the absolute path of the T2 launch JSON), so the agent answers "what model/effort are you running at" from a READ (the stanza and/or the file), not an inference; unlink with the other session configs.
- [ ] T4 — Red-on-pin-drop test: assert the resolved effort actually lands in the LAUNCH RECORD (the registry row and `${cfgBase}-launch.json` written by a spawn through the real `spawnSession` wiring, or its extracted pure helper), pinned to a concrete member of the CLI-accepted set — so deleting the T1 pin (or the T2 stamp) turns a test red instead of silently reverting to a harness default; mirror the `codex-build.test.ts` pinned-and-overridable shape for `NEUTRON_REPL_EFFORT`.
