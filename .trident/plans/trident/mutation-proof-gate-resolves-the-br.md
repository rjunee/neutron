- ROUND-4 (review of the published tip) FIXED FOUR THINGS the earlier rounds got wrong, all in `trident/mutation-prover.ts`:
  1. NO-LOCAL-REF was FALSE, not merely unproven. `git fetch` writes THROUGH a symbolic ref: with `refs/remotes/origin/<b> -> refs/heads/injected` planted, the production refspec created `refs/heads/injected` at the remote tip (reproduced on git 2.43.0). A symbolic destination now DISQUALIFIES the remote-tracking step — no fetch, no read — and resolution falls to the object-verified `expected_head`. Pinned by a real-git test that snapshots `refs/heads` around the call.
  2. The local read used the BARE name, so a TAG of the same name (git's disambiguation prefers `refs/tags/`) or a 40-hex-shaped branch name answered for the branch. It now reads `refs/heads/<branch>`; `null` (a legacy row) keeps the `HEAD` path.
  3. `isPlainBranchName` excluded `_`, refusing valid names (`git check-ref-format --branch _feature` exits 0). `_` is now admitted wherever git admits it.
  4. `branchNameRejection` reported "git rejects this name" even when git NEVER RAN (spawn failure / watchdog kill). Those now read "could not be RUN, so the name is unverified" — both still refuse; the durable reason no longer sends an operator to fix the wrong thing.
  Also: the residual bare-name `rev-parse run.branch` inside `prove()` now goes through `resolveMergeHeadSha`, so ONE primitive resolves a head in this file; and the realgit hostile-name test asserts repository STATE before per-payload outcomes, so a failure cannot shadow the assertions the test exists for.
- VERIFIED: every round-4 fix is mutation-sensitive — removing the symbolic guard, the `+` in the refspec, or the `refs/heads/` qualification each turns the new tests RED (checked one at a time, source restored after each).
