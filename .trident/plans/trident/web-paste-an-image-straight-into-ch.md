## Round 4 — Argus findings closed (2026-08-31)

- BLOCKER (foreign-editor gate missed two real editable spellings): `EDITABLE_SELECTOR` was the attribute literal `'input, textarea, [contenteditable=""], [contenteditable="true"]'`, so a paste aimed at a `contenteditable="plaintext-only"` field — the form a single-line rich editor uses — or at a node that is editable only by INHERITANCE (the caret sits on an inner `<span>` that carries no attribute of its own) read as non-foreign, was `preventDefault()`ed out of that field and stolen into the chat draft. Replaced by `closestEditable()`, a hand-walked ancestor scan: `textarea` and text-taking `input`s are editable; otherwise the nearest element that DECLARES `contenteditable` decides, with `""`/`true`/`plaintext-only` (case-insensitive) editable, `false` an explicit opt-out, and `inherit`/invalid deferring upward. The attribute is read rather than `HTMLElement.isContentEditable` because that property is not uniform: happy-dom reports the browser-`true` spelling `contenteditable=""` as `'inherit'`.
- NIT (the other half of the same selector): a bare `input` also matched checkbox/radio/range/color/file/button inputs, which cannot receive a paste at all — one holding focus would have made a page-level Cmd-V "foreign" and silently dropped the screenshot, the exact failure this card removes. `NON_TEXT_INPUT_TYPES` now excludes them; a real text input beside one stays foreign.
- MINOR (generic-name allow-list too narrow): `withPasteName` renamed only `''` and the exact literal `image.png`, so a clipboard JPEG/WebP (`image.jpeg`, `image.webp`, same generator) still rendered two identically-labelled chips. Now `/^image\.[a-z0-9]+$/i`. The items themselves never collided — the draft keys by generated id — so this was always the display half of req 5.
- NIT (teardown leaked a listener on failure): each test unmounted as its LAST statement, which a failing assertion skips, leaving the surface's document `paste` listener live for every test after it (one real failure printed as several). Mounts now register in a list torn down in `afterEach`, which also removes the container.
- KNOWN AND KEPT (unchanged from round 3): `withPasteName` still rewrites a file genuinely named `image.png` — nothing in the event distinguishes it from the generated one, and the generic case dominates on a paste.
- NOT DONE, deliberate: a clipboard image with an EMPTY MIME type is still ignored (the drop path lets one through to the server sniff). No shipping engine was shown to emit one, and accepting type-less clipboard files on a DOCUMENT-level listener would re-open the "a copied `.zip` raises the import banner" regression round 2 closed. Tracked as a robustness gap, not fixed here.

## Round 5 — Argus findings closed (2026-08-31)

- BLOCKER (a claimed pin that did not pin): the test titled "the library's own paste path stays pinned off" could not detect deletion of `addAttachmentOnPaste={false}` — Argus reproduced 15/15 green with the prop removed. The reason is that assistant-ui's own paste-to-attachment handler returns early unless BOTH that prop and `thread.capabilities.attachments` are true, and this app registers no attachments adapter, so the library path is inert today and NO observable state can distinguish the prop from its absence. The prop is future-proofing, so it is now pinned as what it is: a new case wraps `ComposerPrimitive.Input` through `mock.module` (real bindings re-exported, snapshot restored in `finally`, the discipline `switch-render-cost.test.tsx` established) and asserts every render of the composer input is handed `addAttachmentOnPaste === false`. The old case keeps only the claim it can carry — "focus in the composer attaches exactly once" — and its comment now says why it cannot carry the other one.
- MINOR (CONFIRMED, comment wrong): `withPasteName` returns a NEW `File`, and that File is what `uploads.ts` puts on the wire, so a pasted `image.webp` is UPLOADED as `pasted-N.webp` — not display-only, as the comment implied. The comment now states the rename reaches the wire, and why that is intended and harmless (the server content-addresses the blob and derives its own storage name, so the uploaded name is a label, not an identity).
- NIT (two tests weaker than they read): the `defaultPrevented` passthrough case asserted only "0 items" and could pass on a listener that never registered — it now pastes the same file uncancelled on the same mount and asserts it attaches. The composer text+image case compared `input.value` to a `before` that was `''` on both sides; the composer is CONTROLLED, so the input is now seeded through the native value setter plus an `input` event (what a keystroke does) and the comparison is `'already typing'` vs `'already typing'`.
- NOT DONE, deliberate (unverified, minor): a page-level image paste is still intercepted while the modal Activity Inspector is open, because the gate reads "is the chat surface parked under `[hidden]`", which a modal does not do. Changing the gate to "what is the user looking at" means teaching a document listener about every overlay on the page; the observed outcome is a chip staged in a composer the user reaches by closing the modal, which is reversible and user-initiated. Recorded, not fixed here.
- NOT DONE, deliberate (nits, all unreachable today): `NON_TEXT_INPUT_TYPES` omits `date`/`number`/`time`/`search` (no such input exists anywhere in `landing/chat-react/*.tsx`); an empty-MIME clipboard image is still dropped (round 4 records why); a parameterised MIME (`image/jpeg;q=1`) would synthesize a junk extension. None is producible by a shipping clipboard, and each fix widens a document-level listener for a shape no engine emits.
