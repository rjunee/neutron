## 2026-09-16 — A start is witnessed by its created run

### What changed

`work_board_start` now awaits a `work-board-start-dispatched` stage event after `dispatchBoardBoundBuild` returns the created row and before it reports `status: 'dispatched'` (`trident/work-board-build-tool.ts:402-425`). The ledger row is keyed by the created run id, and its metadata names the board item (`trident/work-board-build-tool.ts:411-415`). A REPL accepting the tool message is therefore no longer the success witness; the run-keyed stage event is.

The targeted test drives the real registered tool, reads the created run back, and requires exactly that stage and metadata on that run (`trident/work-board-build-tool.test.ts:412-426`). Existing rejected paths still return before the new write: an unknown item returns at `trident/work-board-build-tool.ts:344-350`, an already-running item returns at `trident/work-board-build-tool.ts:356-364`, and a chokepoint refusal returns at `trident/work-board-build-tool.ts:402-405`.

### Decisions and invariant

The event is written at the tool boundary rather than inferred from the chat acknowledgement. The acknowledgement is optional and follows the new awaited write (`trident/work-board-build-tool.ts:416-425`), while `recordStageEvent` durably appends the supplied run id, stage, timestamp, and metadata (`trident/store.ts:1068-1077`). That ordering continuously maintains the invariant: a successful `work_board_start` reply follows both creation of its run row and its run-keyed dispatch witness; it does not depend on the REPL or chat sender remaining available.

This value joins the open stage-event vocabulary. The timing taxonomy enumerates only stages used for measured segments (`trident/stage-attribution.ts:3-10`) and alternatives (`trident/stage-attribution.ts:74-76`), so the new name is passive telemetry by default rather than a new state or verdict. It still participates in the existing newest-stage timestamp used as positive liveness evidence (`trident/store.ts:1080-1103`). No `unknown` result was collapsed into a refusal or false result; the tool's existing success/refusal output remains unchanged (`trident/work-board-build-tool.ts:402-425`).

### Correction after review

The first cut **awaited** the stage-event write. A review lane showed, with a throwing
`recordStageEvent`, that this lets a telemetry failure report a run that really started
as a failed tool call — the caller retries and the second dispatch collides with the
first. A witness must not be able to falsify what it witnesses.

The write is now `fireAndForget('work_board_start.dispatch_witness', …)`, matching the
orchestrator's treatment of its analogous stamp, and the rejection is logged rather than
swallowed. A new case pins it: with a throwing ledger the dispatch still reports `ok`,
the run row exists, and the witness was ATTEMPTED (not silently skipped).

Mutation: restoring the `await` (verified landed at `work-board-build-tool.ts:419`) reds
exactly that case — 29 pass 1 fail. Restored; 30/30.
