## Gate instrument audit

### Scope and method

I examined nine gate modules, selected by enumerating the lane's named priority list against `trident/gates/*.ts`: review readiness, review CI, review suite, review panel, review progress, review artifact, build transition, fix lineage, and project admission. This is deliberately not a complete census. For each module I read the inventory row, predicate, call site, and value supplier. The seven verdict columns mean: P = no demonstrated mismatch, F = demonstrated finding, N = note (a concern without a refusing/accepting counterexample), and — = the question does not apply. “P” is scoped to the property quoted in that row, not a proof over all possible inputs.

### Findings and demonstrating cases

#### F1 — readiness cannot establish complete produced-check evidence

The supplier asks `gh pr view` for `statusCheckRollup` and returns only the resulting array, with no total count or completeness witness (`trident/production-host-effects.ts:113-119`). It then reduces every returned row to only `{name,state}` (`trident/project-observation-sources.ts:41-53`). The predicate has no field from which it could distinguish a complete list from a truncated prefix (`trident/gates/review-readiness.ts:4-12,44-52`). This is narrower than G046's explicit complete-list-and-valid-count subject (`docs/trident-gates-inventory.md:120`).

The absence check was `rg -n 'checks|total_count|pageInfo' trident/gates/review-readiness.ts trident/project-observation-sources.ts`: its positive control found the `checks` field at `trident/gates/review-readiness.ts:11`; it found neither a count nor pagination witness in those two files.

Demonstrating case: a known observation containing one required `ci` row in `passed` state returned `{"kind":"passed","failed":[]}` in a direct Bun invocation of `classifyReviewReadiness`. The accepted object has no completeness witness because the observation type exposes none (`trident/gates/review-readiness.ts:4-12`). The same accepted bytes can therefore describe either the complete rollup or a prefix omitting another row. This is a too-permissive and cannot-see finding, not merely a suspicion.

#### F2 — an untrusted suite assertion grants a clean assessment

The source reads a build/fix checkpoint and passes its `report` through (`trident/project-observation-sources.ts:69-78`). The type explicitly calls that report an untrusted claim (`trident/gates/review-suite.ts:20-21`), but `testsPassed === true` returns `known([])` without any host execution receipt (`trident/gates/review-suite.ts:41-43`). A direct Bun invocation using a full-suite dispatch and only `{testsPassed:true}` returned `{"kind":"known","findings":[]}`. The repository's existing test also pins that acceptance (`trident/gates/review-suite.test.ts:24-28`). That contradicts and is narrower than “an unproven full suite forces rejection” (`docs/trident-gates-inventory.md:137`).

#### F3 — panel approval is ultimately derived from worker-authored verdicts

The panel correctly rereads all enabled seat records and compares the live trailer with recorded synthesis (`trident/gates/review-panel.ts:71-97`), so one unaffiliated trailer cannot approve by itself. However, the source creates the `argus-approved` checkpoint solely when the synthesis worker's decoded verdict says APPROVE (`trident/project-review-source.ts:127-141`), and the gate treats that checkpoint as its final approval condition (`trident/gates/review-panel.ts:109-116`). All substantive verdict payloads come from completed worker results (`trident/project-review-source.ts:69-100`). Thus workers can satisfy the value the gate keys on; host storage proves provenance and agreement, not correctness. Under question 6's stated rule, this is a finding even though it is multi-worker corroboration.

#### F4 — unreadable recorded work is treated as ownership evidence

For an uncontained branch, the predicate proves descent from the prior base, but checks descent from the recorded head only when `git cat-file` says that object is readable (`trident/gates/project-admission.ts:59-73`). If that observation fails for any reason, the function allows. The existing test demonstrates both a null head and an unreadable recorded head returning allow (`trident/gates/project-admission.test.ts:90-95`). The comment calls this an “unreadable-object exception” (`trident/gates/project-admission.ts:65-67`), while the inventory requires the prior pin and recorded work to establish this run's ownership (`docs/trident-gates-inventory.md:83`). The code's exception is too permissive and its local prose describes a weaker rule than the inventory.

### Value-supplier pass for question 6

Readiness and CI values come from credentialed host commands (`trident/production-host-effects.ts:51-72,113-119`) and are converted by host code (`trident/project-observation-sources.ts:27-68`); a worker cannot write those values through the reviewed interfaces. Suite identity, strategy, and scope are supplied by host configuration, but the decisive report comes from the build/fix checkpoint (`trident/project-observation-sources.ts:10-16,69-78`), producing F2. Panel identities and dispatch records are host-owned, while verdict payloads are worker results (`trident/project-review-source.ts:69-100`), producing F3. Progress identities and counts are computed from decoded panel findings (`trident/gates/review-panel.ts:98-100`) and not copied from a progress trailer. Review-artifact values are compared against the host snapshot and brief integrity (`trident/gates/review-artifact.ts:12-24`). Build-transition takes branch text from the worker payload but compares it with host assignment (`trident/gates/build-transition.ts:3-9`); merge and landed facts come from measured snapshots (`trident/build-run.ts:318-337`). Fix lineage and project admission use host command results (`trident/gates/fix-lineage.ts:13-24`; `trident/gates/project-admission.ts:21-26`).

### Outcome vocabulary and continuous maintenance

These modules join the existing `GateResult` vocabulary of allow, blocked, and unknown, while review assessment additionally uses known findings (`trident/gates/review-readiness.ts:14-18`; `trident/gates/review-suite.ts:8-10`). The build driver turns blocked into a terminal block and unknown into a terminal unknown before review continues (`trident/build-run.ts:443-460,471-472`). This report introduces no new outcome or invariant. Existing host acquisition and per-transition comparisons maintain the audited checks continuously at review and build boundaries (`trident/build-run.ts:318-356,441-466`).

### Verification and deliberate exclusions

The changed-path enumeration was `git status --short`, whose positive control was this report and whose only output path was this report; therefore no production code or test was changed. Because no guard was added, there is no guard mutation to perform; the mutation table is: new guards — none, mutations — not applicable. Demonstrating commands were direct read-only Bun invocations of `assessReviewSuite` and `classifyReviewReadiness`; their outputs are recorded under F1 and F2. `bun test trident/gates/review-readiness.test.ts trident/gates/review-suite.test.ts trident/gates/review-panel.test.ts trident/gates/project-admission.test.ts` passed 29 tests with 196 assertions. `bunx tsc --noEmit` completed successfully. The root package defines no lint or typecheck script (`package.json:57-62`), so there was no repository lint command to run. I did not run the full suite and did not inspect release-readiness, local merge, or build-claim deeply enough to claim seven-question verdicts for them.
