## Issue #555 — Close shared-config execution during proof-tree provisioning

### What changed

Every proof-tree add now receives a command-line `core.fsmonitor=false` override
beside the existing hooks-path override (`trident/mutation-prover.ts:2697-2712`).
Before each add, the prover reads the effective Git configuration, enumerates
every configured `filter.*.smudge` and `filter.*.process` key, and shadows each
command with an empty value at command-line precedence
(`trident/mutation-prover.ts:2766-2785`). The initial add and the restored-
observation add both consume the resulting arguments
(`trident/mutation-prover.ts:2970-2986`,
`trident/mutation-prover.ts:3027-3038`).

If the effective command family cannot be read or parsed, the prover does not
add a worktree (`trident/mutation-prover.ts:2781-2785`,
`trident/mutation-prover.ts:2978-2981`). This outcome joins the existing
`MutationEvidence` refusal vocabulary: `refuse` records `observed: null` and
`proved: false` (`trident/mutation-prover.ts:2753-2762`). The gate therefore
defaults to blocking the proof rather than provisioning with unknown commands.

### Decisions and invariant

A fixed filter-name list cannot cover Git's named driver family. The prover
instead enumerates the effective names immediately before each provisioning and
uses the same highest-precedence `-c` mechanism as the hooks defense
(`trident/mutation-prover.ts:2703-2712`,
`trident/mutation-prover.ts:2776-2785`). Both `smudge` and the long-running
`process` form are neutralized because either can serve checkout conversion
(`trident/mutation-prover.test.ts:477-497`). Empty filter commands preserve
committed bytes; the real-Git smudge fixture demonstrates that the planted
driver survives while the restored guard remains red
(`trident/mutation-prover-realgit.test.ts:1846-1885`).

The invariant is maintained at the operation that needs it: each proof-tree add
is preceded by config discovery and receives the overrides directly
(`trident/mutation-prover.ts:2977-2984`,
`trident/mutation-prover.ts:3027-3035`). It does not require a branch-authored
guard or control to cooperate. An inspection failure refuses before the first
add, as the unit fixture verifies with a reached-config positive control and an
absent add (`trident/mutation-prover.test.ts:501-509`).

ordinary add appends a marker, while `core.fsmonitor=false` leaves it unchanged
(`trident/mutation-prover-realgit.test.ts:1825-1844`). The filter case plants a
real shared-config driver and verifies both its survival and its inability to
manufacture restored GREEN (`trident/mutation-prover-realgit.test.ts:1846-1885`).

### Validation

`bun test trident/mutation-prover.test.ts
trident/mutation-prover-realgit.test.ts` passed 273 tests with 1,763 assertions.
The restored named mutation checks also passed: two unit cases and two real-Git
cases. `bash scripts/ci/lint.sh` passed every reported gate.

`bash scripts/ci/typecheck-all.sh` checked 51 projects. The changed Trident
project and root project passed. The matrix remained red only because the app
project could not resolve the implicit `@types` library before source analysis;
its config extends Expo and declares no such explicit type entry
(`app/tsconfig.json:1-20`). The same tracked diff query over `app` and the known-
present changed prover returned `trident/mutation-prover.ts` and no app path, so
the branch does not change that project.

### Deliberately not changed

The checked-out-byte verifier remains as defense in depth for conversion and
materialization that is not an external command
(`trident/mutation-prover.ts:2856-2874`). No feature flag, alternate proof path,
new evidence schema, or new verdict was introduced. `SPEC.md` was not changed:
this closes execution paths already inside the proof-isolation design rather
than changing product behavior. The full test suite was not run, as required by
the bounded lane instructions.
