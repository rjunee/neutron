## Issue 563 — cross-project Work Board add

### What changed

`work_board_add` now advertises the optional `target_project` project-id selector while every other tool registered by this surface remains bound to the active project (`work-board/agent-tool.ts:250-282`, `work-board/agent-tool.test.ts:73-84`). The add handler validates a requested id before deriving the board scope (`work-board/agent-tool.ts:292-299`), then sends both an optional plan document and the deterministic acknowledgment to that same destination (`work-board/agent-tool.ts:312-334`).

Production supplies the validation dependency from the canonical live-project enumeration (`open/composer.ts:6813-6821`). That enumeration filters deleted and archived rows (`gateway/projects/sqlite-store.ts:318-340`), and the composition layer threads the dependency into the tool surface (`gateway/composition/input/misc-input.ts:395-397`, `gateway/composition/build-core-modules.ts:249-267`).

### Decisions

The selector is a project id, matching the project settings identity (`gateway/http/app-projects-surface.ts:79-82`). It exists only on add because the requested outcome is posting a new card elsewhere; the test enumerates the names returned by `registerWorkBoardToolSurface`, including conditionally registered removal, and checks every non-add schema (`work-board/agent-tool.test.ts:73-84`).

An unknown destination, or a runtime without the authoritative resolver, joins the existing mutation-result vocabulary as `{ ok:false, error }`; the output schema already accepts that outcome (`work-board/agent-tool.ts:110-118`), and its default is a visible tool refusal with no write (`work-board/agent-tool.ts:291-295`, `work-board/agent-tool.test.ts:153-179`). The live-project list continuously maintains the invariant that a destination remains selectable only while it is active (`gateway/projects/sqlite-store.ts:318-340`); validation does not depend on the requested destination doing any work.
