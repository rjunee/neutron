## 2026-09-16 — Bound project-session acquisition and exercise its uncertainty paths

### Change and acceptance evidence

The spawn await now races an independent 35-second timer. Expiry returns
`unknown` with an acquisition-specific explanation; `finally` clears the timer
on success, rejection, and expiry (`open/wiring/project-build.ts:225-237`).
The budget is independent of the role wall (`open/wiring/project-build.ts:46-55`).
The host event-loop timer maintains the bound without requiring prewarm to settle.
It cannot preempt synchronous event-loop blockage or kill a warming process.

This joins the existing acting-turn uncertainty vocabulary:
`runtime/workers/project-runners.ts:138-146` preserves the explanation as
`unknown`; `trident/build-run.ts:330-334` stops with `unknown`, while a capability
refusal becomes `blocked`. The timeout therefore neither authorizes work nor
asserts that starting a session is impossible. The deadline return precedes
session selection and submission (`open/wiring/project-build.ts:234-249`).

The fixture can register missing, pending, empty, exited, and ready pool entries
under independently chosen keys and options
(`open/__tests__/project-build-e2e.test.ts:508-520`). Cases were enumerated from
the four existing uncertainty messages at
`open/wiring/project-build.ts:216,236,241,244,246`, plus the new timeout:

- Eight failure shapes assert the exact unknown outcome, spawn count, zero
  submissions, and zero PRs (`open/__tests__/project-build-e2e.test.ts:598-628`).
- Ready, exited/replaced, and changed-map-key sessions reach merge, with unrelated
  project and substrate entries present as filter controls
  (`open/__tests__/project-build-e2e.test.ts:631-646`).
- An unresolved prewarm returns the timeout explanation; releasing it afterward
  causes no submission (`open/__tests__/project-build-e2e.test.ts:649-688`).
  Only the acquisition timer is accelerated. The independent abort watchdog makes
  a missing deadline return a wrong answer rather than time out the test.
- The existing cold-start success test still reaches merge
  (`open/__tests__/project-build-e2e.test.ts:703-706`).

### Decisions

Use one fixed acquisition deadline, with the same allowance documented for
conversational prewarm (`open/composer.ts:7468-7474`). Read the existing timer
exemplar first: `open/composer.ts:7481-7488` races and clears its timer, but its
best-effort success return does not communicate uncertainty, so it was not
reused as the acquisition verdict. No configuration switch or alternate path
was introduced. No product decision in SPEC.md was changed.

Leave session identity selection intact. The project factory installs a project
resolver (`open/wiring/substrates.ts:318-319`) while the conversation instance
prefix is established at `open/wiring/substrates.ts:262`. The resolver supplies
`opts.project_id` (`gateway/wiring/build-llm-call-substrate.ts:904-906`). Pool keys
include both instance and project (`runtime/adapters/claude-code/persistent/pool.ts:301-306`),
supervision retains the options under that key
(`runtime/adapters/claude-code/persistent/supervision.ts:51-54`), and adoption
publishes the session at that same key
(`runtime/adapters/claude-code/persistent/boot-adoption.ts:2839-2842`). The adoption
log truncates keys to 32 characters
(`runtime/adapters/claude-code/persistent/boot-adoption.ts:848`); a displayed
instance prefix alone cannot establish which project was adopted.
