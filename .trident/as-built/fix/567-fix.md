## Issue 567 — Chat attach exposes diagnostic files and names refusals

### What changed

The app web composer now includes `.gz`, `.json`, `.log`, and `.csv` in its default file-picker filter at `app/components/InputComposer.tsx:874`. The browser chat defines the same diagnostic suffixes once at `landing/chat-react/ChatApp.tsx:1736-1738` and uses that list for both ordinary attachment picks and active history-import picks at `landing/chat-react/ChatApp.tsx:1846-1850`.

Failed staged attachments now show the stored explanation inline at `landing/chat-react/ChatApp.tsx:1716-1720`. The upload path already retained that explanation under the existing `error` status at `landing/chat-react/useAttachmentDraft.ts:26` and `landing/chat-react/useAttachmentDraft.ts:105-113`; the change does not add a parallel outcome or a new default. Unknown thrown values continue to become `upload failed` at `landing/chat-react/useAttachmentDraft.ts:106-112`, and the renderer has the same fallback at `landing/chat-react/ChatApp.tsx:1719`.

### Decisions

The picker filter is intentionally broader than the upload allow-list. A picker filter controls what the chooser exposes; it does not establish server support. Files still enter the existing upload guard at `landing/chat-react/uploads.ts:245-259`, and the server remains authoritative after client preflight at `landing/chat-react/uploads.ts:260-291`. This makes diagnostic evidence selectable while producing a named refusal instead of hiding the file or reducing the result to a generic failure.

The web constants avoid two separately maintained diagnostic lists: `IMPORT_FILE_ACCEPT` extends `CHAT_FILE_ACCEPT` at `landing/chat-react/ChatApp.tsx:1736-1738`. The app surface remains a separate implementation and is pinned independently by `app/__tests__/attachment-picker-types.test.ts:5-13`.

### Deliberately not changed

The gateway allow-list was not broadened: `gateway/http/app-upload-surface.ts:69-81` supports raster images, PDF, and voice-note audio, while magic-byte detection only recognizes its documented binary formats at `gateway/storage/binary-types.ts:216-223`. Treating arbitrary text or compressed bytes as supported would be a backend product and security decision outside this issue’s picker-and-refusal scope.

The attachment storage contract and product decisions were left unchanged; this change is limited to client selection and visible refusal behavior.
