## 2026-09-17 — the host's own scope decides whether a missing suite exit code is expected

### What this branch delivers

Three commits, enumerated with `git log --oneline origin/main..HEAD`: `588f3a1b`, `94230a81`, `2879aaa2`.

**The defect was found by a live run, not by reading code.** Run `36497522`, a dispatched Work Board card, planned, built, handed off to round two and published PR #1152 green — then died with `Host-observed review suite exit code is missing or unreadable`. Nothing was wrong with the build.

On an intermediate round the host sets `scope: 'subset'` itself (`open/wiring/project-build.ts:433`) and deliberately omits `hostExitCode` (`:456-459`), because nothing ran to produce one. The gate then tolerated that only when the **worker** also emitted the literal string `deferred`. This run's worker honestly reported `suiteOutcome: "failed-preexisting"`, so the exemption missed and the run was killed terminally.

### The delivered behaviour

- A `subset` round with no `hostExitCode` is decided by the host's scope (`trident/gates/review-suite.ts:52-55`). No `suiteOutcome` value can make it terminal.
- `failed-preexisting` keeps its meaning through the existing evidence vocabulary — blocker without evidence, advisory finding with it — extracted to one helper (`:30-35`) shared by the subset and full-suite paths instead of duplicated.
- `report === null` keeps its own diagnostic, **tested before** the subset exemption (`:51`). `report?.hostExitCode === undefined` is also true for a null report, so the order is load-bearing.
- A missing or non-integer `hostExitCode` on a **full-suite** round is still `unknown` (`:56`).

### Corrections this record previously got wrong

An earlier version of this record claimed `applyReviewSuite` only propagates blockers or preserves the panel result. **That is false.** `trident/gates/review-suite.ts:69` returns the suite assessment when it is `unknown`, so an unknown suite overrides an approving panel: `applyReviewSuite({ kind: 'approve' }, { kind: 'unknown', detail: 'receipt unreadable' })` returns the unknown. Adversarial review demonstrated it; the claim is withdrawn.

The same version cited the subset guard at `:46-49` (it is `:52-55` after the ordering fix), reported 8 tests where the file now has 9, and omitted the null-order mutation entirely.
